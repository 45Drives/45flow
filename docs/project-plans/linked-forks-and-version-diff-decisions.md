# Linked Forks and Version Diff: Decisions

Decisions for [linked-forks-and-version-diff.md](linked-forks-and-version-diff.md), recorded as they are confirmed.

| # | Decision | Resolution | Rationale | Unknown it resolves | Territory |
|---|---|---|---|---|---|
| 1 | Automatic change detection | Out of scope. No pixel diffs for images or PDF pages, no changed time ranges or masks for video. Removes plan Phase 3 (steps 9–12), the comparison side of `asset_jobs`, the comparison cache, and the comparison-job API. | User decision 2026-11-16. It is the most expensive and least certain part (FFmpeg analysis, job queue, recipient-scoped caches, coverage disclosure). Forks, publishing and manual comparison stand on their own. | Removes "can automatic detection be accurate and cheap enough", rather than answering it. | Server: `asset_jobs` (comparison kind), comparison-job routes. Player: changes panel, diff workers. Both `package.json` files (no diff engines). |
| 2 | Text/code line diff | Skipped for now. Text/code comparison is two panes of the actual version content, with no added/removed highlighting. | User decision 2026-11-16 ("skip text diff for now"). Can come back later as a browser-only addition. | n/a | Player: text viewer in compare mode. No jsdiff dependency. |
| 3 | Video comparison timeline | Both sides share one timeline bar: one playhead and one scrubber that drives both players. | User decision 2026-11-16. Replaces the "timeline with highlighted changed ranges" in the mockup. | Shapes the video sync work in plan step 7. | Player: `VideoPlayer.vue`, the new comparison sync coordinator, `ShareView.vue` compare layout. |
| 4 | Video alignment | No offset. Both videos always start together at 0. The bar runs to the longer video's end; the shorter side shows an "ended" state past its end, never a frozen frame. Seeking to *t* puts both players at *t*. | User decision 2026-11-16. Removes plan decision 4's manual alignment, the alignment control and the "B +0.00 s" label. | Removes "how is alignment set and kept"; drift and buffering sync remain. | Player: comparison sync coordinator, compare toolbar in `ShareView.vue`. |
| 5 | Explicit publishing | Deferred to a later phase. This phase keeps today's access rule: a recipient may view and compare any version of a file attached to the link (`assertVersionInLink`, `houston-broadcaster/server/api/transcodes.js:71`). A fork is a separate file, visible only once attached to the link. No `link_version_publications`, no `links.history_policy`, no per-link review target, no legacy conversion. | User decision 2026-11-16. Comparing exposes nothing recipients can't already pick in the version selector, and publishing is most of the original Phase 1's work and risk. | Removes "can every serving route enforce a publication allowlist without breaking old clients" from this phase. | Server: no changes to `linkFiles.js` access rules, `reviewDecisions.js` review target, or SSE/download routes for publication. |
| 6 | Media shown in each compare pane | Each pane shows only its own version's media. Video plays that version's HLS, or its proxy MP4 if there's no HLS. If neither exists, the pane shows "Preparing vN for playback…" and the server queues that version's transcode through the existing job; it never shows the live file or another version. Both panes use the same quality level (Data Saver applies to both). Images: the watermarked-image lookup must use the requested version (today it substitutes the latest, `transcodes.js:1678-1700`); if that version's watermarked image is missing, the pane shows "preparing". | User accepted recommendation 2026-11-16. A comparison that silently shows the same media twice is worse than none. | "Can an old version be shown faithfully?" Yes, by on-demand transcode plus a strict per-version lookup. | Server: `api/transcodes.js` version stream and watermark lookup (1612–1700), transcode job queueing for a given `asset_version_id`. Player: pane loading and preparing states. |
| 7 | Fork dialog | Opened from Link Details → Versions. Source shown read-only (file + version). Name pre-filled `<base> - fork.<ext>`, optional variant label. Folder defaults to the source's folder, changeable with the existing folder picker. An existing name is a `409`, never an overwrite. "Add to this link" checkbox, off by default. | User accepted recommendation 2026-11-16. A fork stays private until deliberately attached, which matters now that publishing is deferred (decision 5). | Settles the fork entry point and visibility. | App: `LinkDetailsModal.vue` Versions tab, new fork dialog component. Server: fork route (validates name and destination), link file attachment via the existing link-files update. |
| 8 | Fork copy and recovery | Background job with progress. Copy to a hidden temporary file in the destination folder, then rename into place. Copy-on-write clone where supported (ZFS/Btrfs), otherwise a full copy; never a hardlink. An idempotency key per request: a retry returns the same job. On restart: delete leftover temporary files, mark the job "Failed (server restarted)", user retries; no resume. Disk full: clear failure, no partial file. File, asset, v1 and the `forked_from_version_id` link are written in one transaction only after the rename succeeds. | User accepted recommendation 2026-11-16. Resume adds most of the complexity for a rare case. | "Can a fork copy be interrupted without leaving partial or duplicate forks?" | Server: new fork job table (fork kind only, decision 1 removed comparison jobs), fork route in `api/files.js`, startup cleanup, `database/db.js` and `init_db.py` schema. |
| 9 | Which pairs can be compared | Any two versions in one family (a root file plus all forks descending from it): same-file versions, fork against any source version, sibling forks. Same media kind only (video/image/PDF/text); mixed pairs are `400` and not offered. Recipients: both files must be attached to the link; unattached family members are never named, return the same `404` as an unknown ID, and are left out of lineage responses. "Forked from X vN" is shown to a recipient only when X is attached. Staff compare through the share page too (revised by decision 14). | User accepted recommendation 2026-11-16. | "What may a recipient compare without revealing unshared work?" | Server: comparison-context route and lineage route (family walk over `assets.forked_from_version_id`), recipient filtering. Player: version/file pickers in compare mode. |
| 10 | Comments and approvals in compare mode | Comments on either side via an A/B switch (default B), saved with that side's `asset_version_id` and time/page anchor using the existing comment API. Clicking a comment seeks both players (shared timeline, decision 4). Unsent drafts are guarded on file/version change. Approval controls are hidden in compare mode ("Approve or request changes from Preview"); each side shows its review state as a read-only badge. Review target stays as today (file's latest version). | User accepted recommendation 2026-11-16. Approving a pair has no meaning. | Settles discussion/review behavior without a per-link review target (decision 5). | Player: `CommentsPanel.vue`, `ReviewDecisionPanel.vue` (hidden in compare), `ShareView.vue`. Server: no comment or review-decision schema change. |
| 11 | Free/Pro | No new license restriction: forks and compare work on Free and Pro. Existing Pro comment features (`server/api/premiumComments.js`) keep their current rules inside compare mode. | User accepted recommendation 2026-11-16. Compare is mainly a recipient view, and the obvious premium part (automatic detection) is out (decision 1). Closes the plan's "Open Policy Decision". | Commercial packaging. | No license middleware on new routes. Existing premium checks unchanged. |
| 12 | Deleting a fork's source | Never. A version that any fork was made from, and its retained snapshot, cannot be deleted by any path: version delete (`api/files.js:427`, including `force=1`), artifact/snapshot delete (`api/files.js:506`), link-delete cleanup (`api/links.js:4094`) and project-delete cleanup (`api/projects.js:506`). Direct version and snapshot deletes return `409` naming the forks. Link and project cleanup still complete, but skip fork-source versions and their snapshots and report them as kept (refined 2026-11-16 after mapping the delete paths). Enforced in application code (foreign keys are switched off during migrations, `database/db.js:160-201`). Versions that are not fork sources keep today's delete behavior. If the source file is removed outside 45Flow, the fork keeps working and shows "Forked from X vN (no longer available)". | User decision 2026-11-16 ("focus just on forks … block all deletion"). | "Can lineage and compare inputs disappear underneath a fork?" No. | Server: `api/files.js` delete and artifact routes, project/maintenance cleanup paths, a shared "is fork source" check. App: Versions tab shows the reason instead of a failing Delete. |
| 13 | Compare on phones | Below 768 px: video and images stack A above B with one shared timeline and controls below; both keep playing in sync; tapping a pane makes it full width, with an A \| B toggle. PDF and text use the A \| B toggle only. Comments in a bottom drawer. 768 px and wider: side by side with the right-hand comments panel. No sideways scrolling at 390 px. | User accepted recommendation 2026-11-16. | "Is compare usable on a phone?" | Player: `ShareView.vue` compare layout, `ResizableColumns.vue`, comments drawer. |
| 14 | Where staff compare | **Compare with…** in Link Details → Versions opens that link's share page in compare mode with the chosen pair preselected (deep link). Staff see exactly what the client sees; an unattached fork must be attached first. No compare screen inside the management app this phase. | User accepted recommendation 2026-11-16. The app has no dual media viewer; an internal one would be a second compare UI with its own access risk. Revises decision 9. | "Where does staff comparison happen?" | App: `LinkDetailsModal.vue` Versions tab (Compare with… builds the share-page URL). Player: deep-link query parsing in `ShareView.vue`. |
